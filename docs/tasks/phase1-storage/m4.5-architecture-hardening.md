## 3. M4.5 目标 interface 与 seam

### 3.1 TenantContext / TenantResolver

建立一个可信 identity 到 tenant 的单向解析 seam：

```text
Inbound identity
  -> TenantResolver
  -> TenantContext
  -> StorageRuntime / session / memory / dashboard / proactive
```

Interface 必须明确：

- tenant 只能由服务端可信 channel/auth identity 派生，不能接受客户端任意 `tenant_id`。
- `TenantContext` 至少承载稳定的 `tenant_id`；是否同时承载 principal/channel 等字段应由真实调用需求决定，不预先塞入无用字段。
- 多用户入口禁止隐式回退到 `"default"`；单用户兼容入口若保留默认值，必须显式隔离并有测试。
- session key 不是 tenant identity，不得仅靠解析 session key 作为安全边界。

**M4H-2 定案的 per-channel tenant 策略（2026-08-21，决策：一律多用户派生）**：

| 通道 | tenant 来源（可信身份） | tenant_id 形式 | 状态 |
| --- | --- | --- | --- |
| Telegram | `Update` 的 `chat_id`（私聊=user，群聊=group） | `telegram:{chat_id}` | 已启用，M4H-2 接线 |
| QQ | OneBot 事件的 `group_id`/`user_id` | `qq:{chat_id}` | 已启用，M4H-2 接线 |
| CLI | 会话指定 chat_id（默认 `direct`） | `cli:{chat_id}` | 显式 single-user 入口 |
| programmatic | 调用方显式指定 chat_id（默认 `direct`） | `programmatic:{chat_id}` | 显式 single-user 入口 |
| WebChat | JWT `token.sub`（设计规格，`migration_checklist.md`） | 实现时定案 | 未启用，代码 fail-closed |
| Feishu | 待定 | — | 未启用，代码 fail-closed |

群聊语义：群 `chat_id` 作为单一 tenant（群内成员共享记忆），与现有 session 语义一致。
派生入口：`infra/storage/tenancy.py` 的 `resolve_tenant` / `tenant_id_for_channel`，
适配器在入站边界调用一次，tenant 经 `InboundMessage.tenant_id` 显式贯穿。
完整 M4H-2 计划见 [`m4h-2-tenant-wiring.md`](m4h-2-tenant-wiring.md)。

### 3.2 Storage interface

在调用方和 adapter 之间建立小而稳定的 interface：

- interface 描述调用方依赖的方法、返回值、事务/异常、生命周期和性能约束。
- SQLite 与 PostgreSQL 分别作为 adapter 满足同一 interface。
- 不要求在本阶段重写所有 30 多个方法，但不能继续把具体实现联合类型传播到业务层。
- factory/runtime 负责 adapter 生命周期，调用方不得自行创建 PG connection。

### 3.3 StorageRuntime 与阻塞模型

需要先记录 ADR 级决策，再编码。允许二选一：

1. 推荐目标：async adapter + 进程级 async pool；
2. 过渡方案：sync pool + 有界 executor，所有同步 DB 调用离开 event loop。

无论选择哪条路线，都必须满足：

- pool 配置真实生效；
- 不按 tenant 创建长期 connection/store；
- 不跨并发请求共享同一个 cursor/connection；
- transaction 失败后连接可恢复；
- shutdown 显式关闭 pool/executor；
- `worker_count * pool_max` 有全局预算；
- 有 event-loop lag、pool wait、query latency 指标接入点。
