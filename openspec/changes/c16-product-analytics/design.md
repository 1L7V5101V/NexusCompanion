## Context

产品度量的数据来源已经存在。规范化消息、turn、登录会话与凭据、入站记录、出站投递意图与尝试、跨端绑定、附件、persona 审计、记忆条目都已进入 PostgreSQL（见 `alembic/versions/` 下 C1/C1B/C2/C5/C6/C9/C10/C15 各迁移）。这些表按 `data-retention` 规格不受过期裁剪影响的是业务消息与会话本身，观测类数据则按三档裁剪。

约束来自三处已落码的契约，不是推测：

- `core/telemetry/label_policy.py` 的 `ALLOWED_METRIC_LABELS` 与 `FORBIDDEN_IDENTITY_LABELS` 已把 `account_id`、`turn_id`、`message_id`、`session_key` 等排除在指标 label 之外，注册期 fail-fast（C12 ADR-4）。
- `core/telemetry/audit.py` 的 `AdminAccessAuditEvent` 已定义 `view_content` / `drill_down` / `export` / `enable_content_capture` 四类动作，retention 归 audit 档（C12 ADR-7）。
- `bootstrap/auth/service.py` 已有单一 admin principal（`AdminAuthService`、独立 admin cookie）并逐步写 admin 审计（C5）。

规模前提：Pilot 目标 10–30 个受邀账号、5–15 个并发会话（`openspec/PILOT_ROADMAP.md` §2）。这个数量级决定了度量的正确形态是「人可读的逐账号事实」，不是统计推断。

动机见 `proposal.md` — Why。行为契约见 `specs/product-analytics/spec.md`。

## Goals / Non-Goals

**Goals:**

- 一个只读派生层：从既有事实表算出活跃/回访、激活漏斗、通道分布、主动推送回应、功能采用面。
- 口径集中声明，且能被契约测试固定住。
- 账号键控结果只在 admin principal 下可达，跨 tenant 下钻复用既有审计事件。
- 与既有指标导出面、保留档、内容采集默认态零冲突。

**Non-Goals（设计层面，补充 proposal 的 scope 排除）:**

- 不引入新表、新 job、新外部依赖，也不引入前端状态持久化。
- 不做通用「查询构建器」或指标 DSL；首版每个度量是一段具名查询。
- 不追求跨进程一致快照；一次视图请求内允许极短时间不一致，但同一请求内 SHALL 使用同一时间窗参数。

## Decisions

### D1 派生优先，不建采集管道

**结论**：产品度量全部由既有事实表查询派生，不新增事件表、不新增上报端点、不新增埋点。派生不出的交互登记为缺口。

**备选与不选理由**：

- 备选 A：新建 `product_events` 事件表 + 客户端上报。不选。在 30 账号规模下，客户端交互埋点带来的增量信息极少（关键决策——是否回访、是否完成绑定——服务端本来就看得见），代价却是新增写路径、新增保留档归属、新增隐私面，以及与 C12 已冻结的采集边界发生正面冲突。
- 备选 B：接 PostHog / Umami 一类自托管分析。不选。`PILOT_ROADMAP.md` §2「明确不做」已排除另起炉灶建设独立后台；且外部分析平台要求把账号标识送出进程边界，与「账号维度不得进入指标导出」的既有契约方向相反。

**可核验依据**：`openspec/specs/data-retention/spec.md` 明确业务消息与会话不在保留期执行范围内，因此派生窗口内的历史事实是稳定可读的。

### D2 账号键控数据走查询，不走指标导出

**结论**：需要按账号解析的度量只经 SQL 派生 + 管理员端点返回；指标导出面保持无账号维度。

**理由**：`FORBIDDEN_IDENTITY_LABELS` 已在注册期 fail-fast，放宽它等于推翻一条已合并、并被 C8/C15 沿用的契约（`openspec/PILOT_ROADMAP.md` §「PROPOSED DEFAULT」行记录 label 白名单由 C12 固化）。产品度量的正确出口是「有访问控制的数据查询」，这正是 §5.9.17 给身份字段指明的落点。

**备选**：为产品度量单开一个带账号 label 的私有导出。不选——同名概念两套规则是后续误用的入口。

### D3 口径以 fixture 单一来源，契约测试比对

**结论**：活跃判定、日界与时区、去重主体、跨通道归并、主动推送回应的窗口，集中声明在一个契约 fixture 中；派生层与前端都引用同一份，契约测试比对声明与实现一致。

**理由**：仓库已有同构先例——`tests/fixtures/observability_event_schema.json` 作为事件 schema 单一来源，`tests/fixtures/chat_protocol_frames.json` 作为协议契约单一来源。沿用这个模式而不是发明新模式。

**备选**：口径写进 `config.toml`。不选——配置可被无痕修改，口径漂移不可见；契约需要测试可断言，fixture 更合适。

### D4 呈现形态：逐账号绝对计数优先

**结论**：视图主表为「账号 × 时间窗」的绝对事实（是否活跃、最近活跃时间、各通道计数），任何比率与其分子分母同处展示。

**理由**：30 个账号时 1 个账号等于 3.3 个百分点，只给百分比会把噪声读成趋势。这个形态同时直接回答「具体是哪几个账号没回来」，而运维指标导出回答不了。

### D5 复用现有 Dashboard，不新建后台

**结论**：产品视图作为现有 dashboard 的一个只读区块，端点挂在既有管理面路由下，鉴权复用 admin principal。

**理由**：`PILOT_ROADMAP.md` §2 已定「管理端复用现有 Dashboard，并只增补 Pilot 所需账号管理页面」。`bootstrap/dashboard_api.py` 已同时持有指标导出与管理员侧读路径，`frontend/dashboard/` 已存在，无需新 shell。

### D6 首版即时查询，不物化

**结论**：不建物化视图、不加周期 job；每次请求在限定时间窗内即时派生。

**理由**：30 账号规模下聚合成本可忽略，而物化会立刻带来失效策略与保留档归属两个新问题（规格里已预先约束「若物化则归 operational 档」，但首版不需要触发它）。

**重开条件**：出现可复现的证据表明度量查询影响主链路延迟（有 turn 耗时对比数据），再另起 change 引入物化。

### D7 主动推送「回应」的口径定义

**结论**：以「一次出站投递成功后，同会话内在配置窗口内出现的首个用户入站」计为回应；窗口可配置，默认值以口径 fixture 声明，不作为红线阈值。

**理由**：这是 Pilot 最核心的产品问题（主动推送到底有没有价值），且完全可从出站投递意图/尝试与入站记录派生。沿用 C12「基线报告前不冻结 SLO 红线」——窗口是口径参数，不是判定阈值，视图不显示"达标/未达标"。

## Risks / Trade-offs

- **派生查询扫到观测类大表，拖慢同库主链路** → 强制有界时间窗（规格要求无界请求被拒绝或收敛到默认窗口）；只读事务；走既有 bounded executor，不新开无界并发。
- **口径在前后端各算一份导致漂移** → D3 的 fixture 单一来源 + 契约测试；视图与导出数值不一致被判缺陷（规格已写成契约）。
- **「活跃」被主动推送触发的入站灌水**（系统推一条、用户回一条，算不算活跃）→ 口径声明中按触发来源区分，度量同时给出「用户主动发起」与「回应式」两类，不合并成单一数字。
- **小样本被误读** → 视图标注账号总数 n；比率必带分子分母（D4 与规格同向）。
- **C12 尚未归档，其 `observability-privacy` 主规格还没 sync** → 本 change 只依赖已落码的 `label_policy` 与 `audit` 实体，不依赖 C12 的 spec 同步时机；若 C12 后续调整白名单，本侧只可能变宽松、不会变非法。
- **隐私边界外溢**（管理员为了「看懂」而把消息内容带进产品视图）→ 规格要求响应不含内容原文，审计事件本身也经脱敏；视图字段集为封闭列表，超出即需新需求。
- **Trade-off**：派生层能回答的，是「已经落库的行为」。纯客户端行为（停留、滚动、点开预览、未提交的操作）在本设计下永远看不见。接受这个盲区，因为补齐它的代价与收益在 30 账号规模下不成比例。

## Migration Plan

1. 部署为纯读增量：新增派生查询模块 + 管理端点 + dashboard 只读区块，无 alembic 迁移、无配置必填项。
2. 端点默认挂载在既有管理员鉴权之下；上线即生效，无需开关。
3. **回滚**：摘除产品视图路由与前端区块即可完全回退；因无写入路径、无 schema 变更，回滚不产生任何数据残留或清理动作。
4. **前向依赖**：无。不要求 C12 先归档，不要求 `p0-retention-wiring` 之外的任何未完成项。

## Open Questions

- 记忆增长是否值得进产品视图（`memory_items` 可派生，但它更像运维诊断量，不是用户行为）。
