## Context

调查确认了三件此前不知道的事，它们决定了本 change 的形状。

**一、运行数据已经在采集，但是在旁路 SQLite。** `workspace/logs/` 下有 `passive.db`、`proactive.db`、`drift.db` 三个库，`turn_logging/turn_logger.py` 按 turn 写入，字段含 `turn_type`、`llm_model`、`llm_response`、`tool_calls`、`retry_attempts`、`skill_names`、`input_tokens`、`output_tokens`、`cache_hit_tokens`、`turn_duration_ms`、`error`、`session_key`、`channel`、`chat_id`、`metadata`。`bootstrap/dashboard_api.py:506` 的 `LogDashboardReader` 已经在读它们做日志查询。第五层的 token 数据、第二层的链路归属、第三层的工具调用与重试，主体都来自这里。

**二、旁路日志与业务事实不在一起，且没有保留治理。** 这三个库不在 PostgreSQL 的 tenant 边界内，`core/telemetry/retention.py` 的三档归属不覆盖它们。同时 `turn_logs` 的 `messages` 列是 `NOT NULL`——全量对话内容无条件落盘，这与 C12 已冻结的「message content 默认不进入任何日志存储」相冲突。本 change 不修这个冲突（见 Non-Goals），另开 fix change；本设计只依赖其现状，并明确不扩大其内容面。

**三、四处真缺口。** 全仓无模型价格表（`price|pricing|per_1k` 零命中）；无首字耗时（TTFT）采集；记忆召回结果不落任何持久痕迹（`memory_retrieval` 与 `memory_context_guard` 在 `agent/core/passive_turn.py` 执行，但无记录）；**没有任何用户反馈通路**（`feedback|thumbs|rating|dislike` 在前后端与通道层零命中，只有着色器里的同名变量）。另外，阶段级 trace 在 `core/telemetry/trace_store.py`，是**进程内环形缓冲，默认上限 4096 条 span**，只有显式 `dump_json` 才落盘——所以 turn 内阶段步数的历史分位数不能当作全量数据统计。

**四、正文本来就存在业务库里，但本设计不用它。** `canonical_messages` 有 `content` 列，所有租户的消息正文为支撑对话、跨端同步与记忆而保存。质量判定不读它：读正文推断满意或纠正，要么调模型要么定规则，两者都是在对受邀用户做内容分析，且追问与纠错在文本上形状相近、误判方向系统性偏乐观。改用显式评价，得到的是用户主动给出的结论，不是推测。

规模前提：Pilot 目标 10–30 个受邀账号（`PILOT_ROADMAP.md` §2）。动机见 `proposal.md` — Why；行为契约见 `specs/product-analytics/spec.md`。

## Goals / Non-Goals

**Goals:**

- 五层度量全部可产出，且每层的口径能被契约测试固定。
- 一个跨业务事实与旁路日志的只读派生层，加一个受控下钻链路。
- 质量信号只来自用户显式评价与可观测行为，不来自正文分析；评价覆盖不到的部分明确标注为未评价。
- 与既有指标导出面、保留档、隐私默认零冲突。

**Non-Goals（设计层面，补充 proposal 的 scope 排除）:**

- 不合并 `turn_logs` 与 PostgreSQL，不搬迁历史数据，不改 `turn_logs` 的写入 schema。
- 新增表仅限消息级评价一张；除此之外不引入新表、新 job、新外部依赖。
- 不做通用查询构建器或指标 DSL；首版每个度量是一段具名查询。
- 不追求跨进程一致快照；同一请求内 SHALL 使用同一时间窗参数。

## Decisions

### D1 派生为主，新增采集仅限三处

**结论**：度量主体从既有事实派生。新增采集三项——消息级显式评价、记忆召回痕迹、流式首字耗时。其余缺口登记不补。

**备选与不选理由**：

- 备选 A：新建统一事件表，把五层度量都接到一条新采集管线上。不选。`turn_logs` 已经把最有价值的 turn 级字段落盘了，重建一条管线等于同一事实两个出处，且要付迁移与双写代价。
- 备选 B：接自托管分析平台。不选。`PILOT_ROADMAP.md` §2「明确不做」已排除另起后台；外部平台要求把账号标识送出进程边界，与 D2 方向相反。

### D2 账号键控数据走查询，不走指标导出

**结论**：按账号解析的度量只经 SQL 派生 + 管理员端点返回；指标导出面保持无账号维度。

**理由**：`core/telemetry/label_policy.py` 的 `FORBIDDEN_IDENTITY_LABELS` 已把 `account_id`、`turn_id`、`message_id`、`session_key` 排除在 label 之外，注册期 fail-fast（C12 ADR-4），且该白名单被 C8/C15 沿用。放宽它等于推翻一条已合并契约。身份字段的正当落点是「有访问控制的存储」，这正是 §5.9.17 的原文指引。

### D3 口径以 fixture 单一来源，契约测试比对

**结论**：活跃判定、日/周/月窗口边界与时区、开闭规则、去重主体、跨通道归并、对话开启切分间隔、有效交互规则、跨库归并键，集中声明在一个契约 fixture；派生层与前端引用同一份，契约测试比对声明与实现一致。周与月窗口由日窗口按声明规则合并派生，不各写一套 SQL。

**理由**：仓库已有同构先例——`tests/fixtures/observability_event_schema.json`（事件 schema 单一来源）、`tests/fixtures/chat_protocol_frames.json`（协议契约单一来源）。沿用既有模式，不发明新模式。

**备选**：口径写进 `config.toml`。不选——配置可被无痕修改，口径漂移不可见。

### D4 呈现形态按规模分档，比率必带分子分母

**结论**：账号数低于口径声明的阈值时，主呈现为「账号 × 窗口」绝对事实表；跨过阈值后允许以率为主，但绝对值仍可获得。任何比率与分子分母同处展示。视图标注 n、数据覆盖起点，并区分「零计数」与「无数据」。

**理由**：30 个账号时 1 个账号等于 3.3 个百分点。同时 `turn_logs` 无保留治理、可能只有近期数据，若不显示覆盖起点，一段没有数据的窗口会被读成「用户都没来」。

### D5 复用现有 Dashboard，不新建后台

**结论**：产品视图作为现有 dashboard 的只读区块，端点挂在既有管理面路由下，鉴权复用 admin principal。

**理由**：`PILOT_ROADMAP.md` §2 已定「管理端复用现有 Dashboard，并只增补 Pilot 所需账号管理页面」。`bootstrap/dashboard_api.py` 已同时持有指标导出与 `turn_logs` 读路径，`frontend/dashboard/` 已存在。

### D6 首版即时查询，不物化

**结论**：不建物化视图、不加周期 job，每次请求在限定窗口内即时派生。

**重开条件**：出现可复现证据表明度量查询影响主链路延迟（有 turn 耗时对比数据），再另起 change 引入物化。

### D7 主动推送「回应」与「继续」的口径

**结论**：以「一次出站投递成功后，同会话在配置窗口内出现的首个用户入站」计为回应；回应之后再落静默时长外的入站计为继续对话。窗口与静默时长取口径 fixture，不作为红线阈值，视图不显示达标判定。

**理由**：这是 Pilot 最核心的产品问题，且完全可从出站投递意图/尝试与入站记录派生。沿用 C12「基线报告前不冻结 SLO 红线」。

**明确不可产出的一跳**：推送被「打开」。它需要客户端已读回执，会改动 C4 冻结的协议 fixture。漏斗中该跳标记为不可产出，不跳过、不估算。该跳原本想回答的问题——这条推送是有帮助还是打扰——由该条推送上的显式评价回答（见 D12），两者不合并为同一跳。

### D8 跨库归并键先实测，不靠推测

**结论**：`turn_logs` 侧的连接键是 `session_key`（+ `channel`/`chat_id`），业务事实侧是 `account_id`/`tenant_id`/`conversation_id`。两者的映射关系在实施前必须先以实测确认，确认结果写入口径 fixture；无法对齐的记录进入「未对齐项」并计数呈现，SHALL NOT 静默丢弃。

**理由**：`turn_logs` 的 `session_key` 由 `turn_logging` 侧生成，而 C4 的 hello 握手回的是服务端派生三元组。两者是否可直接换算，当前无证据。**这是本设计唯一一处未证实的前提**，因此列为任务 0 的前置取证，取证失败则下钻链路降级为「按窗口与通道对齐，不按账号对齐」，其余度量不受影响。

### D9 记忆采集复用既有 metadata 字段，不加表

**结论**：记忆召回痕迹（召回是否触发、候选条数、注入条数、被引用条目的标识、结果状态）写入 `turn_logs` 已有的 `metadata` JSON 列，不新增表、不做迁移。只记标识与计数，不记条目正文。

**备选**：新建 PostgreSQL 记忆使用表。不选——需要迁移与写路径改动，而 Pilot 阶段该数据的消费方式只有聚合查询，旁路库已足够；若 D8 取证显示跨库对齐不可行，再评估搬迁。

### D10 成本 = token 实测 × 版本化价格表，缺价不计零

**结论**：token 数直接取 `turn_logs` 的三列实测值。价格表作为配置产物引入，带版本标识；未覆盖的模型标注「成本不可估算」并把该 turn 从汇总中排除、同时给出排除计数。后台任务成本按 `turn_type` 天然分离（`proactive`、`drift` 即用户未发起），不摊入用户发起的交互。每有效交互成本 = 同窗口总成本 ÷ 有效交互数，两操作数同时可见。

**理由**：价格表变更会让历史成本数字漂移，无版本就无法解释。「缺价计零」会把最贵的未登记模型显示为免费，这正是自主任务悄悄烧钱的形态。

### D11 首字耗时按通道可用性呈现

**结论**：TTFT 只在具备流式输出的通道可测（当前为 WebChat）。Telegram 侧无流式语义，该指标按通道分别呈现，SHALL NOT 与非流式通道平均。

**理由**：把不可测通道当零值参与平均，会得到一个看起来精确但没有意义的数。规格中「无数据与零计数可区分」在成本性能层的具体应用。

### D12 质量信号用显式评价，不用文本判定

**结论**：在网页对话通道的每条回复上提供赞/踩两个按钮，评价按消息归属、可改可撤销。有效交互率的分母只含被评价的交互，评价覆盖率与其绝对值同处呈现；未评价的交互不推断为好或坏。

**理由**：这是唯一一个不需要读正文就能拿到用户结论的信号。「不是这个意思」和「再问一句」在文本上形状相近，用规则或模型去区分它们，误判方向系统性偏乐观，等于把猜测包装成指标。显式评价是用户自己给的判断，不存在推断链。

**备选与不选理由**：

- 备选 A：语义模型判定纠正意图。不选。要对受邀用户的全部对话跑批处理内容分析，还要额外花 token；而 Pilot 期一共几十条对话，人工看一眼比模型判得更准。
- 备选 B：关键词模式集合匹配。不选。仍然要读正文，且中文口语里「不是」既能否定也能开头，规则维护成本高于收益。
- 备选 C：只用隐式行为信号（继续、中止、回应推送）。不选为主信号。它会把追问纠错判成深入探讨，方向偏乐观；但保留作为分列指标——中止率与继续率照出，与评价互不替代。

**实现要点**：评价走普通 HTTP 端点，不新增对话帧类型，因此不触碰 C4 冻结的协议 fixture——这一点与「已读回执」不同，后者必须加帧。存储为一张评价表，外键指向规范化消息，`(消息, 评价者)` 唯一约束使改评成为更新而非插入；撤销为删除或置空，但被评价的回复本身不受影响。即时通讯通道当前无内联按钮用法，本期不做，该通道在评价维度呈现为不可评价而非零评价。

**代价一：覆盖率必然低。** 评价是主动动作，多数交互不会被评价，因此有效交互率的样本小且不稳定。规格以「分母只含已评 + 覆盖率同处 + 低于阈值不下结论」三条兜住，不允许把 21/30 读成整体 70%。

**代价二：自选择偏差方向偏悲观。** 愿意点的人常是刚被答错惹烦的人，满意的人多数懒得点。所以这个数字会低估质量，与备选 C 的高估方向相反。两个方向的偏差都保留、分别呈现，比合成一个「中性」数字更可解释。

### D13 运行单位沿用 turn，不引入 run 别名

**结论**：面向用户与代码的度量单位统一为 turn（`turn_id`），不新造 `run_id` 指代同一实体。

**理由**：`turns` 表、`tool_calls.turn_id` 外键、`observability-load` 的 turn 追踪契约已经都叫 turn。再加一个同义词只会让「run 和 turn 是不是一个东西」变成常驻疑问。

## Risks / Trade-offs

- **跨库归并键未经证实（D8）** → 列为任务 0 前置取证；取证失败时下钻降级为按窗口与通道对齐，度量主体不受影响。规格已有「归并失败不静默」兜底。
- **步数分位数取自容量 4096 的进程内环形缓冲，不是全量** → 规格强制声明样本来源与溢出标注；若需要可信历史分位数，须另起 change 把阶段 span 落盘，本 change 不假装能做到。
- **旁路 SQLite 无保留治理，视图窗口可能落在数据覆盖之外** → 标注覆盖起点 + 区分零计数与无数据（D4、规格「呈现不得误导小样本」）。
- **`turn_logs` 全量内容常驻，违反 C12 内容默认不入库** → 本 change 不修、不扩大，登记为依赖项并另开 fix change。风险是产品度量上线会让这份数据被更多消费，从而让「先修内容面」的紧迫性被推迟——需在 fix change 落地前避免把该库暴露到任何非 admin 路径。
- **只读打开旁路 SQLite 可能与写入方争锁** → 只读连接、有界窗口、失败降级为不可用（规格「查询失败不影响对话处理」）。
- **价格表漂移导致历史成本不可比** → 版本化 + 视图标注所用版本（D10）。
- **记忆有效性度量依赖「被模型引用」的可观测性** → 若引用无法从既有输出判定，该子项按缺口登记，不估算。
- **小样本被误读为趋势** → 标注 n、绝对值优先、比率带分母。
- **评价覆盖率低，有效交互率的分母可能只有个位数** → 分母只含已评 + 覆盖率同处 + 低于阈值不下结论（D12 代价一）。
- **评价自选择偏差方向偏悲观** → 与隐式行为信号（方向偏乐观）分列呈现，不合成单一「中性」数字（D12 代价二）。
- **评价是用户产生的内容，误删即销毁输入** → 回滚与后续清理均不删除评价数据；其删除路径归属账号生命周期议题，不由度量能力决定。
- **Trade-off**：纯客户端行为（停留、滚动、未提交的 UI 操作）在本设计下永远看不见。接受，因为补齐它要动已冻结的协议契约，收益在 30 账号规模下不成比例。

## Migration Plan

1. 先做任务 0 的跨库归并取证，取证结论决定 D8 的下钻形态，再动其余实现。
2. 部署为读侧增量 + 一处最小写侧增量：派生查询模块 + 管理端点 + dashboard 只读区块 + 价格表配置项；评价表为 expand-only alembic revision，评价端点与前端按钮随附。`turn_logs` 侧无 schema 变更（记忆痕迹复用 `metadata`）。
3. 价格表为可选配置：未配置时成本项标注不可估算，服务照常启动，不阻塞其余度量。
4. **回滚**：摘除产品视图路由与前端区块即可回退视图；三处新增采集各自可独立关闭，关闭后仅使对应度量不可用，不影响业务写路径。**评价数据不随回滚清除**——它是用户产生的内容，删除即销毁用户输入；回滚只停止采集与展示，历史评价保留在表内。评价表本身为 expand-only，回滚不需要 downgrade。
5. **前向依赖**：无。不要求 C12 先归档；`turn_logs` 内容治理的 fix change 是后续而非前置。

- 记忆条目增长曲线是否值得进产品视图（`memory_items` 可派生，但它更像运维诊断量而非用户行为）。

- 即时通讯通道的评价入口用内联按钮还是指令文本（当前该通道无任何内联按钮用法，需另起 change 接入）。
