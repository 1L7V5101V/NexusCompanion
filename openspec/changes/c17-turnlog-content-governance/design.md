## Context

旁路运行日志由 `turn_logging/` 写入三个 SQLite 单库（`workspace/logs/{passive,proactive,drift}.db`），`bootstrap/dashboard_api.py:506` 的 `LogDashboardReader` 已在读。现状三条事实决定了本 change 的边界：

- 写路径无内容开关。`TurnLoggerConfig` 只有 `db_path`、`flush_interval_s`、`max_batch_size`；建表语句 `messages TEXT NOT NULL`（`turn_logging/turn_logger.py:26`）另有 `llm_response` 列；`turn_logging/` 内对 `redact` 零引用。唯一的门禁 `logging_cfg.enabled` 定义为 `bool(self.passive_db)`，而示例配置三条路径全配着。
- 保留侧对这一形态不可用。`core/telemetry/retention.py` 只做文件 mtime 扫描，`bootstrap/retention/sweeper.py:19` 自述「内置 root 集为空」。而 `openspec/specs/data-retention/spec.md:160` 的既有需求已经写明：对仍在读写的活动数据库，SHALL NOT 以文件修改时间作过期判据，需要清理时 SHALL 走按记录时间裁剪的路径。**契约已经给了答案，缺的是这条路径的实现。**
- 这个库是 C16 第三、五层度量的唯一数据源。token 数、耗时、工具调用序列、重试都只在它里面。

动机见 `proposal.md` — Why；契约见 `specs/turnlog-content-gate/spec.md` 与 `specs/data-retention/spec.md`。

## Goals / Non-Goals

**Goals:**

- 正文默认不落盘，且落不落盘不影响非内容字段的完整性——C16 的度量在默认态照常可用。
- 需要看正文时有短期、可审计、自动失效的开启路径，而不是永久常开。
- 这个库获得可执行的保留归属，同时不删任何历史数据。

**Non-Goals（设计层面）:**

- 不搬迁到 PostgreSQL，不改存储布局，不分片。
- 不实现通用行级保留框架；按记录时间裁剪的实现只服务这一种形态。
- 不改动 `canonical_messages` 的任何行为——业务消息保存是账号生命周期议题。

## Decisions

### D1 开关收口在入库前一处，不在三条链各自判断

**结论**：内容 gate 放在旁路日志的行构造处，单一收口点。三条链（passive / proactive / drift）不感知开关，照常提交完整记录，由收口点决定正文字段是否落盘。

**备选与不选理由**：各链自己判断——不选。三个入口三份逻辑必然漂移，且未来新增链路会漏掉。

### D2 默认关闭，代价由呈现消化

**结论**：默认不写正文，与 C12 已冻结的默认一致。

**代价**：现有 dashboard 的日志查询页此前能翻出对话原文，默认关闭后会是空的。这是用户可见的行为变化。规格以「空正文呈现为未采集而非空字符串」兜住，前端需明确标注并指向短期开启路径。不选「保持默认开启并只加个开关」——那等于把 C12 的默认态留在纸面上。

### D3 历史保留 = 治理生效点之前的行豁免，不改写历史

**结论**：记录一个治理生效点时间戳。按记录时间裁剪时附加条件：早于生效点的行不参与自动裁剪。历史行因此保持原样、不迁移、不改写、不被任何周期任务删除。

**备选与不选理由**：给历史行加一列豁免标记——不选。加列即需回填，回填就是改写历史数据，与本决定要规避的风险同类。生效点是一个时间点判据，不触碰任何既有行。

### D4 新数据按记录时间行级裁剪，不分片

**结论**：实现按记录时间的行级删除，分批执行、幂等、支持演练模式。

**备选与不选理由**：改为按日期分片落库，让既有 mtime 文件清理直接可用——不选。读侧要同时兼容两种布局，`LogDashboardReader` 与 C16 派生层都得跟着复杂化；而既有契约本就为活动数据库指定了按记录时间这条路径，走它不需要新布局。

### D5 保留档随写入时的开关状态确定，不是统一一档

**结论**：一条记录的档位按其**写入时**的开关状态确定——关闭态不含正文，属运行元数据，归 operational（30 天）；开启态含正文，归内容型 debug（7 天）。归属写入时即固定，不随开关后续变化改写。

**理由**：这条同时解决两个否则会出现的问题。若统一归 7 天档，C16 的月窗口聚合会静默失去数据——30 天的窗口需要 operational 档才成立。若按「当前开关状态」判定归属，则一次开关切换会让同一批行的档位漂移，删除行为变得不可解释。

**备选**：统一 30 天。不选——开启态的记录含正文，与 C12 给内容型 debug 定的 7 天短档相冲突。

### D6 顺带修正 drift 的配置注释

**结论**：`config.example.toml:367` 的「漂流探索链路日志库路径」改为按 `PILOT_ROADMAP.md` §3.1 的定义描述：主动链的无动作分支。

**理由**：这行注释是「drift 是一条独立自主探索链路」这一误解的来源之一，改正成本为零。

## Risks / Trade-offs

- **存量正文将无限期驻留。** 这是「历史数据保留」的直接后果，不是疏漏：豁免集只增不减，文件 mtime 又因持续写入而永不超龄。磁盘占用与一旦泄露的影响面都保持现状。缓解：本 change 把该状态显式登记为遗留决定而非隐式默认，后续处置只能显式发起并留审计事件。
- **排障习惯受影响。** 此前可直接翻日志看原文，默认关闭后不行。缓解：保留 D2 的短期开启路径（TTL + 审计），并在运维文档写明用法。
- **裁剪与写入争锁。** 该库处于 WAL 持续写入中，删除需分批小事务、幂等、可中断。缓解：先跑演练模式出报告，人工核对后再启用真删。
- **档位归属被实现成「按当前开关状态」判定。** 会使删除行为不可解释。缓解：规格已写成「写入时确定且不改写」，并有对应 Scenario 可测。
- **与 C16 的耦合被破坏。** C16 依赖非内容字段完整与 30 天窗口。缓解：R2（关闭态字段完整性）与 D5（operational 档）各有一条契约测试固定。
- **Trade-off**：本设计不解决「这份数据该不该存在」，只解决「它不该无治理地存在」。彻底搬迁到 PostgreSQL 是更干净的终局，但那是存储整合议题，不该由一次隐私收口顺带决定。

## Migration Plan

1. **先落 gate**（默认关闭）。这一步立即止血，不删任何数据，可独立发布。
2. 落归属规则与治理生效点记录；此时仍不执行删除。
3. 启用按记录时间裁剪，**首轮强制演练模式**，产出可存证报告并人工核对豁免边界与计数后，才启用真删。
4. **回滚**：裁剪有既有总开关，关闭即停；gate 保持默认关闭不影响其他功能。三步都不删数据，回滚无数据恢复动作。
5. **前向依赖**：无。C16 可先于本 change 实施，但邀请外部账号前本 change 的第 1 步必须已上线。

## Open Questions

- 存量正文最终是否老化、留多久——已明确决定保留，此处仅登记为未决，不在本 change 内处理。
- 关闭态是否保留消息长度或条数这类派生量——会略微泄露对话规模，需单独判断。
- 短期开启内容采集的操作流程由谁审批（Pilot 阶段单人自决，正式邀请后可能需要写进 runbook）。
